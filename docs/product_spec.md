# RigPop

**角色动画与桌宠编辑器**

制作像素角色、部件、配饰、动作和交互，从同一工程导出 Godot 游戏角色包或 Windows 桌宠。

## 当前状态

RigPop 目前处于独立产品的设计阶段。本目录只有项目文档，尚无 `project.godot`、
独立编辑器、角色格式实现或可运行的导出程序。

FlufflightDemo 中已有角色编辑、像素绘制、输入绑定和地图试演原型，可作为后续提取的参考。
这些实现尚未迁移到 RigPop；下文描述产品目标与架构约定，不是已实现功能清单。

开发与 AI 协作请先阅读 [Agent.md](../Agent.md)。本目录是产品独立根目录，未来移动到其他位置或
电脑后应能继续使用，不依赖外层 FlufflightDemo。

## 产品要解决的问题

用户不应为了制作桌宠和游戏角色，重复拆分贴图、制作动作和配置交互。
RigPop 将角色创作过程统一，再为两种运行环境提供对应能力：

| 输出 | 内容与用途 |
| --- | --- |
| RigPop 编辑器 | `RigPop.exe` 创作应用，打开即可创建、导入、编辑和导出角色 |
| Godot 角色包 | 场景、资源、贴图、运行组件与接口说明，可放进 Godot 地图 |
| Windows 桌宠包 | 可直接运行的 `.exe` 及必要依赖，在桌面显示角色并响应交互 |
| 可编辑工程 | 原始部件、姿势图、关键帧、色板和配置，便于继续修改与再次导出 |

主要服务像素角色创作者、桌宠作者及 Godot 独立游戏开发者。
首期聚焦 Windows 和 Godot；其他系统或引擎通过后续适配扩展。

## 独立编辑器与两种试演场景

产品本身也需要发布 Windows 应用。用户双击 `RigPop.exe` 后，能够新建角色、导入已有工程或
角色包、导入美术素材，继续制作并保存。它与导出的角色桌宠程序是两个不同的应用。
首屏提供直接可用的创建、导入与最近工程入口，不要求先打开 Godot。

工作区采用共用编辑内容加两种场景的组织方式：

| 工作区 / 场景 | 主要内容 | 配置归属 |
| --- | --- | --- |
| 共用角色工作区 | 人物库、部件、像素绘制、动作时间轴、控制映射和物理参数 | 角色定义 |
| Godot 游戏角色场景 | 地图移动、碰撞、朝向、移动施法、目标选择、游戏属性和技能测试 | 游戏配置 |
| 桌宠场景 | 桌面移动、点击与抚摸反应、拖拽、屏幕边界、置顶、穿透和快捷键 | 桌宠配置 |

两种试演场景分别有入口 `.tscn`，引用同一角色定义和共用角色视图。
切换场景不会创建两套互不相干的角色，也不会覆盖另一模式的设置。
游戏检查器呈现速度、碰撞、技能等参数，桌宠检查器呈现窗口和桌面交互等参数。

编辑器内可提供嵌入式预览；透明窗口、全局快捷键、多屏和 DPI 等行为，需要启动真实桌面
试演进程验证。场景预览、应用发布和两种内容导出各自有独立入口与状态反馈。

## 目标创作流程

1. 在 `RigPop.exe` 中新建角色，选择人形、非人形模板或空结构，或导入已有角色工程。
2. 导入图片、图集或受支持的 PSD 分层美术，调整部件挂接、枢轴、位置和遮挡，按需添加配饰。
3. 创建动作，在关键帧修改位置、角度、可见性或贴图；大幅变化可以逐帧重画。
4. 按需为配饰设置物理摆动，将键鼠的点按、长按、双击绑定到动作或已支持的行为命令。
5. 在角色预览和地图试演中检查动画、移动、碰撞及动作叠加；在桌面试演中检查桌宠表现。
6. 保存完整工程，选择 Godot 角色包或桌宠程序导出。

人形与怪物使用同一套部件模型。史莱姆可以只有身体、面部和核心，不要求补齐手脚。
配饰是可选部件，能够独立绘制、挂接、分层和制作动画。

像素创作优先采用刚性骨架、部件关键帧和姿势换图，避免将动作局限于贴图压缩或拉伸。
最近邻显示、原始像素绘制、完整选色、取色、色板和可撤销编辑属于基础工作流。

## 审美与交互要求

RigPop 应呈现清晰、精致、适合长期工作的创作工具界面，像素风重点体现在角色与素材上。
软件文字和控件保持可读性，不强制使用小号像素字体，也不使用装饰性大横幅占据工作区。

- 中央是画布，左侧是角色与部件，右侧是属性，下方是时间轴；面板可收起，模式入口稳定。
- 统一字体、图标、间距和控件样式；使用中性背景，选中、关键帧、未保存与错误采用明确语义色。
- 工具用熟悉的图标并带提示；动作命令有清楚名称；参数显示单位，支持精确输入和拖动调整。
- 透明棋盘、深浅背景、参考线、骨骼和遮挡检查可开关，不影响导出美术。
- 显示原始像素大小、画布倍率和实际角色尺度，避免将视图放大误认为修改了素材。
- 新建、导入、空轨道、缺失素材、未保存、导出失败等状态提供完整反馈和可执行操作。
- 普通笔画和关键帧编辑可以撤销，破坏性操作有恢复路径，编辑输入不会误触角色控制。
- 检查 960×640、1280×800、1920×1080 及 DPI 缩放，面板不足时滚动或收起，不遮挡文字和画布。

视觉质量和操作效率都属于验收内容。使用实际角色、中文界面和动画截图检查，不能只确认按钮存在。
角色内容本身也要有审美基线：内置示例应有清晰轮廓、协调色板、自然接缝、稳定枢轴和可读的
动作节奏。提供参考图、洋葱皮和动画对比，在地图与桌面实际显示大小检查观感，不限制用户自定画风。

## 能力边界

- 动画描述外观变化；技能或行为处理器负责移动、弹体、伤害等实际执行。
- 添加一个新动画不会自动产生新的技能机制。已有机制可以通过界面配置，新机制需扩展处理器。
- 地图和桌面共用角色，但碰撞环境、输入来源和可用能力不同。
- 游戏窗口内按键与后台全局快捷键分别实现，导出器需提示目标不支持的交互。
- AI 生成美术可作为未来导入模块，基础编辑不依赖在线服务。
- 首期不建设完整关卡编辑器、通用游戏引擎、账号体系、云服务或商城。

## 技术方案

| 层面 | 选择与理由 |
| --- | --- |
| 桌面与二维引擎 | Godot 4.x；初始以 4.7 系列为基线，复用已有原型经验 |
| 主语言 | GDScript，负责数据逻辑、界面、动画、预览与导出流程 |
| 界面 | Godot 原生 Control 与布局容器，编辑区和各工作区独立组织 |
| 工程格式 | UTF-8 JSON 加素材目录，保持可检查、可迁移和便于 AI 读取 |
| 像素素材 | PNG 等无损资源，最近邻采样，明确画布、枢轴和倍率 |
| PSD | 独立解析适配，提取图层和位置后转换为内部素材；解析库候选需实际兼容验证 |
| 配饰物理 | 可选二级运动模块；复用 Godot 二维物理及成熟骨链组件 |
| Godot 交付 | `.tscn`、`.tres`、贴图、运行插件与 `manifest.json` |
| 桌宠交付 | Godot 导出的 Windows 程序，按构建方式随附 `.pck` 或原生库 |
| 平台扩展 | 需要时用 C++ GDExtension 接入 Windows 系统能力 |

不需要用 C/C++ 重写整个产品。Godot 自身提供 Windows 运行环境，原生扩展用于必要的系统
功能或成熟解析库桥接。开发者构建 RigPop 和桌宠运行宿主时，需要匹配的 Godot 导出模板；发布版编辑器
应携带预构建的运行宿主，用户制作和导出桌宠不必另装 Godot，运行成品也不需要 Godot 编辑器。

## PSD 分层导入

PSD 是美术导入来源，不会自动包含可用的骨架、动作或交互。目标是让用户导入分层原画后，
在 RigPop 中继续装配、绑定和制作动画，减少逐张导出图片的操作。

导入过程应包含预览和映射：

1. 读取画布、图层组、图层名称、顺序、可见性、透明度与位置偏移。
2. 展示图层树与整体合成预览，选择哪些图层作为身体部件，哪些作为表情或姿势候选。
3. 转为内部 PNG 与部件记录，保留原图层坐标；裁边时同步枢轴，避免部件全部居中后错位。
4. 根据名称给出挂接建议，由用户确认；图层组本身不等同于骨架父子关系。
5. 保留原始 PSD 与来源映射，重新导入时检查变化，尽量保留已经制作的动作、部件 ID 和物理配置。

基础支持先聚焦 8 位 RGB/RGBA 栅格图层及图层组。蒙版、剪贴、特殊混合、文字、智能对象和
图层效果需要兼容测试；不能还原的内容应给出报告，并允许用户先栅格化、经确认合成或使用
分层 PNG。初期不承诺完整 Photoshop 编辑能力、PSD 回写或 PSB 大文档支持。

Godot 不能通过普通图片加载流程直接得到这里需要的 PSD 图层模型，需独立解析适配。
优先评估成熟库，例如封装 `psd-tools` 辅助进程，或采用合适的原生解析库；不从零编写 PSD
解析器。若采用辅助进程，其解释器、库与必要资源随编辑器提供，用户无需安装 Python 或 Photoshop。
解析器只输出中间素材和导入报告，后续可替换实现，不影响动作、物理和两种导出。
PSD 解析只在创作端执行，普通桌宠和 Godot 角色运行组件不携带这套导入依赖。

导入已有 RigPop 工程或角色包时恢复完整编辑数据；导入 PSD 或图片时建立美术部件。
这两类导入使用不同入口，避免让用户误以为一张图片已经具有完整角色行为。

## 类似 Live2D 的物理编辑体验

目标是为头发、耳朵、尾巴、围巾和披风提供可调的二级运动，让角色在移动、转向或拖拽后
自然摆动。可以借鉴 Live2D 的参数面板和预览方式；这不代表已接入 Live2D SDK，也不承诺
直接打开 `.moc3` 模型。

| 项目 | 计划能力 |
| --- | --- |
| 作用对象 | 在预览中选择部件、设置锚点和骨链，定义跟随与摆动关系 |
| 参数 | 重力、惯性、刚度、阻尼、摆幅、角度或长度限制及混合权重 |
| 运动来源 | 移动、转向、拖拽、动作或可配置外力 |
| 编辑反馈 | 单独启停、复位、慢放、查看约束范围，与动画同时预览 |
| 持久化 | 配置随角色保存，必要处理器随 Godot 角色或桌宠导出 |

实现采用独立二级运动模块，优先评估成熟弹簧或骨链组件；需要真实接触、刚体或关节时使用
Godot 二维物理。基础角色和静态图片不强制启用物理模块。

处理顺序为 **基础动作与叠加动作 → 二级运动偏移 → 像素合成与显示**。
内部模拟保留连续数值，显示时再量化到像素网格，避免物理每一步取整后失去小幅运动。
物理不会代替大动作换图，也不会自动覆盖手工关键帧；作用范围和混合权重需要明确。
暂停、换角色、拖动时间轴时提供一致的复位或预滚规则，预览与导出采用同一版本的处理器。

完整网格变形、布料模拟、复杂 IK 和物理烘焙可后续作为独立能力扩展，不把它们混同于
首期的配饰摆动功能。

## 解耦架构

依赖关系围绕稳定的角色数据与行为接口组织：

```text
                      编辑器工作区
                          |
                 工程 / 素材 / 校验服务
                          |
                 角色定义与通用规则
                          |
                  共用二维运行组件
                     /          \
              游戏运行适配    桌面运行适配
                     \          /
                    各自的导出器
```

上图表示内容使用流程，不表示所有模块相互依赖。具体依赖方向以 [Agent.md](../Agent.md) 为准。
核心数据不引用 UI 或操作系统；游戏适配和桌面适配互不引用。
导出器只携带目标所需的模块，Godot 游戏无需安装桌宠系统扩展。

计划目录如下，当前尚未创建这些实现目录：

```text
RigPop/
  Agent.md              开发约定与 AI 协作入口
  README.md             产品说明与项目状态
  project.godot         独立应用入口，后续创建
  core/                 角色、动作、手势和命令模型
  services/             工程、素材、校验、迁移与模块登记
  editor/               动作、像素、控制及试演工作区
  runtime/
    shared/             共用角色渲染与动作播放
      secondary_motion/ 可选配饰与骨链二级运动
    game/               游戏移动、碰撞与能力执行
    desktop/            桌宠移动、窗口与桌面交互
  exporters/            Godot 与桌宠导出
  platform/windows/     可选系统接口与原生扩展
  extensions/           有实际需求时增加的扩展模块
  schemas/              工程与导出包格式
  docs/                 接口、构建和兼容文档
  tests/                核心、编辑、导出及迁移验证
```

先建立实际需要的模块和接口，不提前创建空插件平台或所有目录。
共用层仍以 Godot 为运行基础，解耦并不意味着能直接在其他引擎执行这些脚本。

## 角色数据与场景放置

可编辑工程的 JSON 与素材是创作数据的事实来源；导出 `.tres` 和 `.tscn` 是目标格式转换。
角色、部件和动作使用稳定 ID，显示名称可以修改。生成资源与用户手写场景分开管理。

| 数据 | 所属层 |
| --- | --- |
| 部件、父子关系、姿势图、图层、动作、色板 | 共用角色定义 |
| 输入绑定、可选能力及参数 | 角色配置，由目标运行层校验 |
| 地图位置、出生朝向、阵营、巡逻路线 | 游戏场景中的放置配置 |
| 桌面位置、屏幕选择、窗口行为 | 桌宠实例配置 |
| 当前动作、按住状态、生命等动态数据 | 运行实例，不回写共享角色定义 |

基础角色无需生命、魔力或伤害字段，相关属性由战斗能力模块扩展。
角色保存不会覆盖关卡中的摆放，也不会将试演中的临时状态写回角色模板。

## 两种导出的约定

### Godot 角色包

单独一个 `.tres` 不足以保证角色在其他项目中运行。角色包需要包含角色入口场景、资源、
贴图、自定义资源脚本或相应运行依赖，并明确兼容的 Godot 与 RigPop 运行 API 版本。

目标项目安装一次共用运行插件，后续角色包复用它，避免复制同名公共类。
导入时先检查兼容性，再把资源引用转换到目标项目内，不能引用作者电脑的原路径。
用户可将角色 `.tscn` 拖入地图，或通过接口由脚本、AI 辅助开发工具实例化。
导出器提供独立运行插件的源文件和资源模板，不从 RigPop 成品中提取编译脚本作为游戏依赖。

导出包中的 `manifest.json` 计划描述：

- 角色 ID、显示名、包版本和兼容要求。
- 入口场景、资源依赖与所需运行模块。
- 动作列表、语义、循环和叠加方式。
- 可调用命令、参数及能力限制。
- 坐标单位、角色原点、碰撞、挂接点及实例配置方式。

清单让 AI 知道如何使用角色。具体放到哪个地图、哪个位置，仍由用户指令或场景放置数据决定。

### Windows 桌宠包

桌宠导出包含选定角色、共用运行组件、桌面适配层及必要平台功能。
目标交互包括点击、拖动、自定义按键与动作；透明窗口、置顶、鼠标穿透和全局快捷键按
平台支持情况启用。透明区域应合理穿透，同时保留恢复设置与退出的入口。

桌宠可以支持输入配置；编辑器本身不必随每个桌宠发布。
具体实现优先采用预构建运行宿主：由产品开发者用 Godot 导出宿主，角色作者在 RigPop 中
生成配置和素材包，由宿主加载。需要 `.pck` 时可使用 Godot 的 `PCKPacker` 生成数据包，
而不是在发布版编辑器内依赖另一份 Godot 主编辑器执行导出命令。

单文件 `.exe` 与带配套文件的目录包都属于可选构建方式，不能把依赖 `.pck` 或原生库的
程序误称为单文件版。每次导出固定运行组件版本，升级编辑器后需重新导出才更新成品。
首期先交付含 `.exe` 的完整目录包，验证依赖齐全与便携性，再增加单文件封装。

## 便携性

需要分别保证三类内容可搬移：

1. **开发源码**：以 RigPop 为根目录，包含所需脚本、素材、字体、构建说明和依赖版本。
   换电脑开发时安装匹配的 Godot；构建程序时另需对应导出模板。
2. **可编辑角色工程**：包含全部导入素材和配置，内部使用相对路径，不依赖 `.godot/` 缓存。
3. **发布程序**：包含运行所需文件，普通用户无需 Godot 编辑器；用户数据的保存位置明确。

提供显式便携模式，将用户数据放在可写的便携数据目录中。程序目录不可写时应清楚提示或
明确切换到系统用户目录，不能悄悄让用户以为复制程序就带走了所有角色。

当前仅有文档，因此尚未完成上述运行和迁移验证。

## 扩展与快速升级

新增功能应通过稳定接口接入对应模块，例如：

| 新功能 | 主要扩展位置 |
| --- | --- |
| 新角色模板或配饰 | 模板数据、素材与可选配置面板 |
| 新动作效果或技能 | 命令及参数定义、对应能力处理器 |
| 新图片或动画格式 | 素材导入器 |
| PSD 兼容性增强 | 分层解析适配器、素材映射和导入报告 |
| 配饰摆动或其他物理 | 二级运动处理器及约束配置 |
| 新桌面系统功能 | 桌面运行层与平台适配器 |
| 新引擎输出 | 独立导出器及目标运行组件 |

扩展通过模块 ID、版本、依赖和支持宿主声明能力。共用模型不为每个功能增加专用字段，
扩展配置放在模块自己的数据区；缺失模块时保留配置并说明不可用的原因。

工程格式升级采用可测试的顺序迁移，迁移前备份；高版本不兼容数据不进行破坏性保存。
应用、工程格式、角色包和运行 API 分别管理版本。内置模块随应用发布，第三方插件热加载和
自动更新服务不是初期承诺。

这种组织方式可以减少新增功能对其他模块的修改，但新能力仍需明确哪些运行目标支持，
并完成相应编辑、试演、导出和兼容验证。
